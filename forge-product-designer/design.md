# 架构设计方法论

## 方案选择

1. 读 `~/.forge/user-profile.json`（如存在），提取历史架构偏好、技术栈和交互深度。
2. 读 `learned_patterns`，结合 brief、features.md 和项目资料识别项目类型（如 CLI）。只筛选明确相关的 pattern 注入方案推荐和架构决策。
3. 向用户推荐大/中/小三种方案，说明取舍，等用户选择：
   - **大方案**：多服务、消息队列、生产级部署与运维。
   - **中方案**：模块化单体、清晰分层、SQLite。
   - **小方案**：单脚本或平铺结构，够用就行。
4. 未收到选择时只输出方案比较和需要确认的问题，不写最终 `docs/architecture.md`。

## 设计与自查

1. 设计分层结构、模块划分、模块边界、数据流和接口定义；每项与 `docs/features.md` 的核心功能对应。
2. 用具体数据样例模拟端到端数据流，至少覆盖一个正常路径和一个失败分支；在架构文档的数据流段写明输入、转换、输出和状态变化。
3. 按裁减表做架构自查，只展开所选方案要求的项目；不凭空增加审查项。
4. 产出 `docs/architecture.md`，严格按以下结构：产品概述 → 架构设计 → 数据流 → 接口定义 → 失败模式 → 技术栈。
5. 在文档中标明所选方案规模、裁减范围、关键假设和未解决问题，便于 product-reviewer 独立审查。
6. 成功写入后更新状态：phase → review，must_fix_count=0，suggestion_count=0，追加 design 到 completed_phases。
