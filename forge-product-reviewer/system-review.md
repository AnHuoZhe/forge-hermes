# Agent 系统审查标准

全部模块中审通过并锁定后执行。读取全量代码、架构文档、模块审查报告和相关测试结果。

本阶段不重复执行完整 module_review 六轴，而是检查 Agent 系统是否形成完整闭环。

## 一级维度

system_review 的一级维度固定为以下六项：

1. LLM。
2. 上下文工程。
3. 工具。
4. 约束。
5. 验证。
6. 纠正。

成本、记忆、可靠性、评估等内容只能作为二级检查项，不改变一级报告结构。

二级检查项固定挂载关系：

1. 成本挂到上下文工程和工具，并与 module_review 的性能与成本检查关联。
2. 记忆挂到上下文工程、验证和纠正。
3. 可靠性挂到工具、验证和纠正。
4. 评估挂到验证和纠正。

## 一、LLM

检查：

1. LLM 是否承担了适合概率性生成的任务。
2. 需要确定性处理的逻辑是否错误地交给 LLM。
3. 模型输出是否被未经验证地当作事实或控制信号。
4. 模型选择是否符合当前任务的复杂度和可靠性要求。

## 二、上下文工程

检查：

1. 系统提示、技能、记忆、用户输入和轨迹是否分层。
2. 是否存在无关上下文污染。
3. 上下文压缩是否可能丢失关键约束。
4. 动态上下文编排是否把不可信内容混入高优先级指令。
5. 技能是否按需加载，是否存在不必要的全量披露。
6. 提示注入是否可能改变高优先级规则。
7. 记忆是否被正确读取、更新和隔离。

## 三、工具

检查：

1. 工具输入是否经过验证。
2. 工具输出、错误和副作用是否定义清楚。
3. 工具权限是否超过任务所需。
4. 工具失败后 Agent 是否能感知。
5. 工具返回值是否经过验证。
6. 是否存在重复调用、无上限重试或错误结果继续传播。
7. 工具成本和外部依赖是否可控。

## 四、约束

检查：

1. 系统约束是否完整。
2. 关键规则是否只存在于提示词中。
3. 重要安全规则是否有权限层或代码层兜底。
4. 多个约束冲突时优先级是否明确。
5. 外部内容是否能够越过约束层改变 Agent 行为。
6. 阶段门禁是否能够阻止未通过结果继续推进。

## 五、验证

检查：

1. Agent 输出是否经过独立验证。
2. 验证是否验证真实结果，而不是只验证过程完成。
3. 核心路径和关键失败路径是否验证。
4. 验证是否有明确的通过标准。
5. 是否存在生成成功即默认任务成功的情况。
6. 是否记录实际执行证据。
7. 评估标准是否与需求和系统目标一致。

## 六、纠正

检查：

1. 验证失败后是否进入纠正路径。
2. 纠正是否会重新规划，而不是重复相同错误策略。
3. 是否有重试上限。
4. 是否记录失败原因。
5. 是否存在错误级联。
6. 纠正是否可能覆盖正确结果。
7. 多次纠正仍不收敛时是否能够退回设计阶段或暂停人工介入。

## 系统级交叉检查

必要时检查以下交叉点：

1. 上下文工程与成本。
2. 记忆与上下文工程。
3. 工具与可靠性。
4. 可靠性与评估。
5. 成本与评估。

交叉检查只在发现跨维度问题时输出，不重复生成同一问题。

## 主归类规则

1. 只影响一个模块的问题，主归类为 module_review。
2. 影响两个及以上模块协作的问题，主归类为 system_review。
3. 影响模块组织、系统边界或长期运行的问题，主归类为 architecture_gap。

层级优先级为 architecture_gap 高于 system_review，system_review 高于 module_review。

一个问题只能有一个主归类。其他相关维度只记录关联编号。

## 证据要求

每个一级维度必须属于以下三种结果之一：

1. 发现问题：提供系统对象、数据流、状态、接口、测试或运行证据。
2. 未发现问题：说明检查对象、检查路径和结论依据。
3. 材料不足：说明缺少的材料、无法确认的结论和后续验证方式。

没有检查对象、检查路径或材料限制说明的“未发现问题”无效。

没有真实数据时，成本、Token、性能、稳定性和评估结论只能标记为风险推测或待验证，不得伪造具体数值。

## 结构性问题

以下问题视为结构性问题：模块职责错位、跨模块数据流断层、状态机缺口、上下文污染、工具边界混乱、验证结果无法反馈、错误处理跨层泄漏、安全边界依赖模型自觉。

必须改的结构性问题必须输出：问题、证据、根因、影响、严重度、重构方案、迁移步骤和验证方式。

建议改的结构性问题至少输出：问题、根因、目标结构和验证方式。

## 边界

大审通过后进入 done。

大审不通过时，必须把问题按主归类映射到受影响模块或设计阶段：

1. module_review 问题回到受影响模块。
2. system_review 问题回到受影响模块和相关数据流。
3. architecture_gap 问题退回 design 或 review。

不得把系统级问题简单拆成模块任务后跳过系统级复审。所有受影响模块和系统链路完成修复后，必须重新执行 system_review。
