# 模块基础审查标准

当前模块所有任务完成并锁定后执行。读取模块代码、相关测试、架构文档和模块输入输出说明。

本阶段执行模块基础审查六轴。六个审查轴必须全部出现在报告中，即使没有发现问题，也必须记录检查结果。

## 一、正确性

检查：

1. 功能是否符合需求。
2. 输入是否经过正确处理。
3. 输出是否符合预期。
4. 边界条件是否正确。
5. 异常路径是否产生正确结果。
6. 状态转换是否符合预期。
7. 是否存在正常路径有效、异常路径错误的情况。

报告必须区分预期行为、实际行为、两者是否一致和影响范围。

## 二、测试与验证

检查：

1. 核心正常路径是否验证。
2. 异常路径是否验证。
3. 边界条件是否验证。
4. 模块接口是否验证。
5. 测试是否覆盖真实行为。
6. 测试是否过度依赖 Mock，导致真实问题被隐藏。

报告必须列出已有验证、缺失验证、缺失验证的风险和最小补充验证场景。

没有真实执行结果时，只能标记为“待验证”，不得写成“已验证”。

## 三、安全

检查：

1. 输入是否可信。
2. 文件、网络、命令和外部服务权限是否超过实际需要。
3. 敏感信息是否可能进入日志、上下文、错误信息或最终输出。
4. 是否存在路径穿越、任意文件访问或未授权调用。
5. 外部内容是否可能改变系统指令。
6. 工具返回值是否可能直接改变 Agent 行为。
7. 技能、记忆和用户输入之间的优先级是否明确。

## 四、可维护性

可维护性只关注未来修改成本，不审查个人风格偏好。

检查：

1. 模块职责是否清晰。
2. 是否存在职责混杂。
3. 是否存在重复逻辑。
4. 配置是否散落。
5. 错误处理是否重复且不一致。
6. 命名是否会误导维护者。
7. 是否存在需要同时修改多个不相关文件的情况。
8. 临时方案是否已经变成核心依赖。

不得把缩进偏好、格式偏好、个人命名喜好或不影响行为的代码风格差异自动判定为问题。

## 五、性能与成本

性能与成本属于同一个审查轴，报告中不拆成两套独立审查。

性能检查：

1. 运行时间风险。
2. 内存风险。
3. 并发风险。
4. I/O 风险。
5. 重复处理。
6. 无上限循环、递归、重试或并发。

成本检查：

1. LLM 调用次数。
2. 上下文增长。
3. Token 消耗风险。
4. 外部服务调用。
5. 网络和存储成本。

没有真实数据时，只能输出已确认问题、风险推测或待验证项。禁止伪造 Token 数量、耗时、性能提升比例、节省金额和稳定性数据。

## 六、接口契约

接口契约只负责模块级接口，不负责完整系统的架构分层。

检查：

1. 输入结构。
2. 输出结构。
3. 字段语义。
4. 错误契约。
5. 上下游兼容性。
6. 空值、异常值和未知字段处理。
7. 副作用边界。
8. 是否直接修改其他模块内部状态。

模块是否放在正确层级、系统整体职责是否错位、跨层架构是否合理，不在本轴处理，归入 system_review 或架构裂隙审查。

## 主归类规则

1. 只影响一个模块的问题，主归类为 module_review。
2. 影响两个及以上模块协作的问题，主归类为 system_review，并记录关联维度。
3. 影响模块组织、系统边界或长期运行的问题，主归类为 architecture_gap，并记录关联维度。

层级优先级为 architecture_gap 高于 system_review，system_review 高于 module_review。

一个问题只能有一个主归类。其他相关层级只能引用问题编号，不得重复生成完整问题。

## 结构性问题

以下问题视为结构性问题：职责错位、模块严重耦合、数据流断层、状态机缺口、上下文污染、工具边界混乱、验证结果无法反馈、错误处理跨层泄漏、安全边界依赖模型自觉。

必须改的结构性问题必须输出：问题、证据、根因、影响、严重度、重构方案、迁移步骤和验证方式。

建议改的结构性问题至少输出：问题、根因、目标结构和验证方式。

可忽略问题不要求输出重构方案。

## 证据要求

每个审查轴必须属于以下三种结果之一：

1. 发现问题：提供检查对象、具体证据、问题表现、影响和严重度。
2. 未发现问题：说明检查对象、检查路径和得出结论的依据。
3. 材料不足：说明缺少的材料、无法确认的结论和后续验证方式。

只有一句“已检查，未发现问题”无效。

## 阶段边界

本审查聚焦模块本身的基础质量，不完整执行 system_review 的六个一级维度，也不重复执行架构裂隙五层分析。

如果发现问题已经超出单模块范围，必须标记对应的 system_review 或 architecture_gap 关联，不得在本阶段自行扩大审查范围。
